# Threat Trace: concept-to-code study map

This map describes the implementation in this repository as it exists. Line references are given as named sections/methods so the mapping remains readable after edits; class and method names are exact. The application currently demonstrates a local synthetic workflow. Items under **Not implemented** are intentionally not claimed as complete.

## 1. OOP mapping

| Required concept | Exact implementation | How the code demonstrates it | Simple explanation |
|---|---|---|---|
| Packages | `src/main/java/com/threattrace/{domain,analysis,persistence,privacy,security,web}` | Java `package` declarations across domain, analysis, persistence, privacy, security, and web classes | Packages group related code and prevent one large source namespace. |
| Interface | `src/main/java/com/threattrace/analysis/SimilarityStrategy.java` — `SimilarityStrategy.compare`; `src/main/java/com/threattrace/analysis/EventParser.java` — `EventParser.parse` | `WeightedSimilarityStrategy` implements the comparison contract; `RelationalEventParser` implements the parsing contract. `ApiController` accepts these abstractions through constructor injection. | An interface states what an implementation must do without tying callers to its concrete class. |
| Inheritance | `src/main/java/com/threattrace/domain/ForensicEvent.java` — abstract base; `ProcessEvent`, `NetworkEvent`, `IdentityEvent`, `FileEvent`, `SystemEvent` extend it | Shared immutable event fields and accessors live in the base class; event subtypes add category-specific behavior. | Specialized event types reuse the shared event structure. |
| Overriding | `ProcessEvent.getCategory/validate`, `NetworkEvent.getCategory/validate`, `IdentityEvent.getCategory/validate`, `FileEvent.getCategory/validate`, `SystemEvent.getCategory/validate` in `src/main/java/com/threattrace/domain/` | Each subtype overrides both abstract methods with its own category and validation rule. | A child class supplies its own version of a parent-declared behavior. |
| Overloading | `src/main/java/com/threattrace/analysis/WeightedSimilarityStrategy.java` — `compare(featuresA, featuresB)` and `compare(featuresA, featuresB, weights)`; `src/main/java/com/threattrace/privacy/EvidencePassportService.java` — `releaseArtifact(id)` and `releaseArtifact(id, format)` | The short overload selects default weights/JSON; the longer overload accepts an explicit weight map or output format and validates it. | Same method name, different parameter list for related choices. |
| Polymorphism | `src/main/java/com/threattrace/analysis/RelationalEventParser.java` — `parse`; `src/main/java/com/threattrace/web/ApiController.java` — `timeline` | The parser creates a subtype through a `ForensicEvent` reference. `timeline` calls `event.getCategory()`, which dispatches to the subtype override. | The same call behaves according to the actual event object. |
| Encapsulation | `src/main/java/com/threattrace/domain/ForensicEvent.java` — private final fields and getters; `src/main/java/com/threattrace/security/InputChecks.java` — `required`, `ids` | Event state is private and immutable after construction. Package inputs are trimmed, bounded, and copied into an immutable list before persistence. | State is kept behind a controlled public interface. |
| Exception handling | `src/main/java/com/threattrace/analysis/AnalysisJobService.java` — `compare`; `src/main/java/com/threattrace/persistence/CaseRepository.java` — transaction callbacks; `src/main/java/com/threattrace/web/ApiController.java` — `error` | Timeouts, queue rejection, interruption, analytics failures, DB failures, and invalid input become controlled exceptions; SQL callbacks roll back before rethrowing; API failures return JSON error responses. | Errors are caught or translated so failed work does not silently look successful. |
| Collections | `CaseRepository` and `ApiController` use `List`, `Map`, `Set`, `ArrayList`, `LinkedHashSet`; `AnalysisJobService` uses a bounded `ArrayBlockingQueue` | Collections hold query rows, feature vectors, selected evidence IDs, comparison dimensions, and queued work. | Collections hold groups and mappings of runtime data. |
| Generics | `src/main/java/com/threattrace/domain/Result.java` — `Result<T>`; `src/main/java/com/threattrace/analysis/AnalysisJobService.java` — `Result<Map<String,Object>>` | The generic result wrapper carries different typed payloads; the analysis service returns a result containing a map payload. Repository callbacks and Java collection declarations also use generic types. | A generic class can safely wrap different data types without duplicating the class. |
| Wrapper classes | `src/main/java/com/threattrace/domain/ForensicEvent.java` — `Integer id/caseId`; `src/main/java/com/threattrace/domain/Hypothesis.java` — `Integer id/caseId`, `Double confidence` | Nullable-capable wrapper types represent database identifiers and decimal confidence values instead of primitive-only fields. | Wrapper objects can represent absent values and work with generic collections. |
| Multithreading | `src/main/java/com/threattrace/analysis/AnalysisJobService.java` — bounded `ThreadPoolExecutor`, `compare`, `close` | Case comparisons run on named worker threads with a fixed core size, bounded queue, rejection behavior, and timeout. This prevents an unbounded task backlog. | Independent analytics work can run away from the request thread under a controlled concurrency limit. |

## 2. DBMS mapping

Primary SQL source: `database/schema.sql`. Synthetic fixture data: `database/seed.sql`.

| DBMS concept | Exact table/object/file | Functional dependency or implementation | Purpose / evidence in the app |
|---|---|---|---|
| Normalization and BCNF | `database/schema.sql`; tables `investigation_cases`, `event_logs`, `digital_twin_nodes`, `digital_twin_edges`, `hypotheses`, `hypothesis_evidence`, `similarity_comparisons`, `similarity_dimensions`, `comparison_input_events`, `simulation_runs`, `evidence_packages`, `package_items`, `package_approvals`, `audit_events`, `mitigation_strategies` | Each relation stores one entity or relationship. Many-to-many case evidence and hypothesis evidence use junction relations. No event IDs, roles, or lists are stored comma-separated. | Separates source facts from hypotheses, derived comparison dimensions, scenario outputs, package selections, approvals, and audit actions. |
| BCNF justification | Same schema | Under the stated keys, non-trivial dependencies have superkey determinants: `case_id → case attributes`; `event_id → event attributes`; `(case_id,label) → twin-node attributes` (unique); `edge_id → edge attributes`; `hypothesis_id → hypothesis attributes`; `(hypothesis_id,event_id,relation) → evidence note`; `comparison_id → comparison attributes`; `(comparison_id,dimension) → dimension result`; `(comparison_id,side,event_id)` identifies each comparison input; `(package_id,event_id) → redaction_mode`; `strategy_id → strategy attributes`. | These determinants are primary or declared candidate keys. Keep this justification synchronized if new non-key dependencies are added. |
| Functional dependencies | `database/schema.sql` table keys and unique/check declarations | The unique key on `digital_twin_nodes(case_id,label)` is the candidate key for a node label within one case. The primary keys listed above determine their remaining row attributes. No dependency such as `profile_id → profile_name` is duplicated in comparison rows because there is no profile-name relation in this MVP. | Makes the BCNF claim explicit rather than equating “has a primary key” with BCNF. |
| Triggers | `trg_event_parent_insert_guard`, `trg_event_parent_update_guard`, `trg_package_status_audit`, `trg_package_release_guard`, `trg_redaction_audit` in `database/schema.sql` | Event insert/update triggers reject an event pointing to itself as its parent. Status updates append an audit row; a transition to `RELEASED` is rejected unless an approval row exists; selecting evidence appends a redaction-mode audit row. | Provides DB-level integrity, workflow, and provenance checks. The event self-parent rule is implemented with triggers because MySQL disallows a `CHECK` expression that references an `AUTO_INCREMENT` column. |
| Views | `vw_case_timeline`, `vw_similarity_explanation`, `vw_asset_exposure`, `vw_package_review`, `vw_audit_history` | Named read projections join or expose the relational records needed by timeline, explanation, exposure, review, and audit queries. | `CaseRepository.audit` reads `vw_audit_history`; the other views are available for study/querying. |
| Stored procedures | `sp_submit_package_for_review`, `sp_approve_package_release`, `sp_expire_packages`, `sp_record_simulation_run` | Procedures verify package state/completeness, commit state transitions, expire packages, or record a versioned simulation. `sp_submit_package_for_review` and `sp_approve_package_release` are called by `CaseRepository`. | Demonstrates MySQL procedure behavior that SQLite would not provide equivalently. |
| Transactions | `src/main/java/com/threattrace/persistence/CaseRepository.java` — `createPackage`, `saveComparison`, `submitPackage`, `decidePackage` | Package and comparison creation use JDBC transactions; state changes and audit effects commit together; exceptions roll back. | Prevents half-written packages/comparisons or approval state changes. |
| Constraints | `database/schema.sql` table definitions | Foreign keys preserve references; enums constrain statuses; `CHECK` clauses bound confidence/criticality/scores and prevent direct self-links; `NOT NULL` protects required fields; unique keys enforce case-local labels and junction uniqueness. | Rejects invalid records at the DB boundary even if an API check is bypassed. |
| Indexes | `ix_event_case_time`, `ix_event_type`, `ix_twin_case`, `ix_similarity_cases`, `ix_comparison_event`, `ix_package_status`, `ix_approval_package`, `ix_audit_case_time` | Composite indexes support event chronology, case graph lookup, comparisons, package queues, approvals, and audit history. | Improves the query paths used by the workbench and supports review retrieval. |
| Similarity reproducibility | Tables `similarity_comparisons`, `similarity_dimensions`, `comparison_input_events` | `CaseRepository.saveComparison` stores weighted score, algorithm version, SHA-256 feature-input digest, each dimension, and source event references, all in one transaction. | A comparison is not silently overwritten when the scoring code changes. |

## 3. Project architecture and data flow

| Path | Responsibility |
|---|---|
| `src/main/java/com/threattrace/ThreatTraceApplication.java` | Spring Boot entry point and component configuration. |
| `src/main/java/com/threattrace/web/ApiController.java` | JSON API for cases, timeline, comparison, twin simulation, hypotheses, package creation/review/export, and audit. Validates route inputs and coordinates domain services. |
| `src/main/java/com/threattrace/domain/` | Immutable event and hypothesis types, UTC-aware JDBC timestamp conversion (`EventTime`), generic result type, and investigation exception. |
| `src/main/java/com/threattrace/analysis/` | Event parsing, similarity interface/HTTP adapter, and bounded analysis executor. |
| `src/main/java/com/threattrace/persistence/CaseRepository.java` | Parameterized SQL, transaction boundaries, procedure calls, and persistence to MySQL. |
| `src/main/java/com/threattrace/privacy/EvidencePassportService.java` | Redacted preview, pseudonymous labels, timestamp generalization, and SHA-256 package manifest. |
| `src/main/java/com/threattrace/security/InputChecks.java` | Required-value, length, and evidence-selection validation. This is input validation, not user authentication. |
| `src/main/resources/application.properties` | Port, JDBC, and analytics URL configuration. |
| `src/main/resources/static/index.html`, `style.css`, `app.js` | Single-page workbench, layout, interactions, and same-origin API calls. |
| `analytics/service.py` | Python standard-library HTTP service; computes five comparison dimensions from minimized features. |
| `database/schema.sql`, `database/seed.sql` | Normalized MySQL schema, programmable objects, and synthetic cases. |
| `mvnw.cmd`, `mvnw`, `.mvn/wrapper/maven-wrapper.properties` | Apache Maven Wrapper 3.3.2 scripts select and bootstrap Maven 3.9.9, so no global Maven installation is needed. |
| `scripts/start.ps1`, `.env.example`, `README.md` | Windows startup loads local environment settings, connects through `mysql.exe`, applies the MySQL schema and seed scripts, starts the Python worker, and launches Spring Boot through `mvnw.cmd`. Docker Compose is not part of the required startup path. |

**Request flow:** Browser `app.js` calls `/api/...` on the Java server. `ApiController` validates and routes the request. `CaseRepository` reads source rows or commits a workflow transaction. Timeline rows pass through `EventParser` into typed `ForensicEvent` subclasses. For similarity, Java reads categorical event features and relative-time inputs, sends only that minimized JSON to `analytics/service.py`, then commits the result, method version, digest, and input event references to MySQL. The Digital Twin simulation stores a versioned hypothetical output. The Evidence Passport path reads selected source events, transforms the preview, records an approval/rejection workflow in MySQL, and permits a JSON export plus SHA-256 only in `RELEASED` state.

## 5. Viva preparation

| Likely question | Answer based on this implementation |
|---|---|
| Why is the timeline not rendered as evenly spaced events? | `app.js` positions each marker using its timestamp divided by the full elapsed interval. Therefore a 40-minute quiet period occupies more space than a two-second burst. |
| What does “inferred” mean here? | It is a seeded synthetic evidence state attached to an event or graph edge. The interface keeps it visually distinct from an observed event; it does not convert an inference into a fact. |
| Is a high Attack DNA score proof of a common attacker? | No. Python compares five behavioral dimensions and explicitly labels the result as a lead, not attribution or a calibrated probability. |
| Which data is sent to Python? | Java queries event category, feature tokens, relative-order timestamps, certainty, and evidence references for the compared synthetic case. Raw logs and full descriptions are not part of the analytics request. |
| How can a comparison be reproduced? | The DB stores the algorithm version, input feature SHA-256 digest, source input event IDs per side, dimension scores, and explanatory references. |
| Why use an interface for similarity? | `AnalysisJobService` depends on `SimilarityStrategy`, while `WeightedSimilarityStrategy` supplies the Python-backed implementation. The caller is decoupled from the implementation. |
| Where does polymorphism occur at runtime? | `RelationalEventParser.parse` returns a `ForensicEvent` subtype; `ApiController.timeline` calls `getCategory()` through the base type and gets the subtype override. |
| How is the package protected from premature release? | Java checks package state and calls MySQL procedures inside a transaction. The release trigger additionally rejects `RELEASED` when no approval record exists. |
| What does the SHA-256 hash prove? | It detects whether the exported generated JSON bytes have changed relative to the manifest. It does not prove source evidence truth, acquisition chain-of-custody, or recipient identity. |
| Does pseudonymization make the data anonymous? | No. Stable labels and generalized times reduce direct identifiers, but correlation with rare behavior or outside information can still identify a source. A human must review the preview. |
| What does the Digital Twin simulation change? | It stores an illustrative result and assumptions in `simulation_runs`. It never calls an endpoint, changes a real asset, isolates a host, or blocks traffic. |
| Why is the database normalized? | Each entity is stored once, many-to-many associations use junction tables, and the documented determinants are keys. This avoids repeated labels and comma-separated evidence references. |
| Why use a bounded thread pool? | Similarity requests can be slower than a local database read. A fixed worker count and queue prevent unlimited background tasks from consuming resources; rejected or timed-out work becomes an error. |
| Why is there no C++ module? | The project idea recommends C++ only when profiling shows a high-volume parser or graph algorithm needs it. This MVP has no measured bottleneck justifying a third implementation language. |

## Implemented scope and known gaps

- Implemented: local synthetic end-to-end journey; working Java HTTP/UI integration; Python feature analytics; MySQL persistence; timeline; explainable comparison; hypothetical twin; evidence hypotheses; review-gated redacted JSON package with stored hash.
- Not implemented: real log ingestion/import UI, authentication, role-based case authorization, verified recipient identity, encryption or external transfer, receipt/correction follow-up, automatic package expiry scheduler, true redaction guarantees, calibrated risk/probability, external agency integration, or C++ acceleration.
- The “approval workflow” is a functional state transition for the local demo, but reviewer identity is a typed label with no authentication. Do not treat this as an operational evidence disclosure system.
- Event lineage cycle prevention covers direct self-parenting in SQL and seeded parent links; the MVP does not provide an import path that validates longer cycles.
